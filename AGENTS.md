# AGENTS.md

Guidance for agents working in this repo. Read `ARCHITECTURE.md` for the data model and request flows; `setup.md` for local setup.

## Project

CoachXYZ — multi-sport AI video analyzer. Three deployable tiers plus shared config:

- `web-next/` — Next.js 16 (App Router) + React 19 + TS + Tailwind v4. Coach dashboard, marketing site, player hub.
- `server/` — Bun 1.x + Elysia. Auth sync, org data layer, BullMQ orchestration, Supabase persistence, email (Resend).
- `engine/` — Python 3.12 + FastAPI. Video analysis pipeline (Gemini + MediaPipe).
- `sports/` — per-sport scoring config JSON. `docs/` — feature docs.

`web-next/proxy.ts` is the Next middleware that forwards `/api/*` to the server.

Local test personas (real logins for every role, no Auth0 Management API app needed): `cd web-next && node scripts/seedPersonas.mjs`, then load a role with `web-next/.personas/<role>.json` as a Playwright `storageState`. ## Frontend conventions (from the skills, reconciled with repo state)

- **Data fetching**: parallelize independent fetches with `Promise.all` (async-parallel) — including RSC bootstrap pairs (`getSession` + `getOrgContext`, profile + org context). Use `unstable_noStore()` on authenticated dashboard pages serving fresh data; nothing to cache, fetches hit the live API. Prefer server components; add `"use client"` only where Web APIs/interactivity are needed.
- **Web errors**: one mapping rule in `lib/errors.ts` (`errorFromResponse` narrows the any-typed wire body; `engineError` shapes engine-layer failures) — never hand-build `CoachAIError` literals in fetch/XHR/SSE paths; narrowed fields fall back instead of leaking non-strings into the UI.
- **No barrel imports.** Import directly (`@/components/org/ScheduleClient`, not `@/components`). Statically analyzable paths only.
- **Primitives**: use `@/components/9ui/ui/*` (avatar, badge, button, card, chart, checkbox, dialog, dropdown-menu, input, label, select, skeleton, sonner, switch, textarea — vendor more with `npx shadcn@latest add @9ui/<name>`). Legacy `components/ui/*` is deleted — do not resurrect. shadcn-style 9ui where available.
- **Re-render hygiene**: no components defined inside components; no synchronous `setState` in effect bodies (defer via `requestAnimationFrame`, move to event handlers, or derive during render); use functional `setState` and lazy `useState(() => ...)` for expensive init; keep non-trivial derived data in `useMemo` (e.g., `byDay` map in ScheduleClient); use `Map`/`Set` for repeated lookups (not `find` in loops).
- **Conditional rendering**: prefer ternaries over `{x && ...}` when the left side could render a falsy number. Watch `.length`-based conditionals.
- **Styling**: Tailwind classes via the semantic token system in `app/globals.css` (`bg-card`, `text-muted-foreground`, `border-border`) — never raw hex or hand-written `dark:` color pairs in `.tsx`; a theme-varying value is a token (add one value-exact). Marketing pages follow the same light/dark theme (the `--marketing-*` alias layer was deleted). Type sizes: prefer the font-size-only utilities `text-label` (11) `text-caption` (12) `text-meta` (13) `text-body` (14) `text-title` (15) `text-lead` (16) over `text-[Npx]` (adopted first-party-wide; only vendored `components/interior/**` keeps literal six sizes); pinned by `lib/__tests__/typeScale.test.ts`. Details in `docs/DESIGN_FOUNDATIONS.md`. Mobile-first.
- **Client data arch**: the app does not use SWR/React Query — plain `fetch` with in-flight race guards. Don't add a data-fetching lib without asking.
- **Remote state transport**: analysis and AI-report progress use authenticated SSE (`startAnalysisStatus` / `subscribeAiReportEvents`); Redis/BullMQ events wake the stream, while `GET /api/job-status/:jobId` is only a hard-capped reconciliation fallback. Keep browser polling out of normal user-visible flows; use bounded one-shot reads for refresh/reconnect.
- **Voice/structure**: functional components, descriptive boolean names (`isLoading`, `hasError`), lowercase-with-dashes dirs, TS. Keep new shared components in the repo's existing `export default function` style.

## Server/API conventions

- Logging: winston via `lib/logger.ts` — never bare `console.*` in server src; keep the `type` event field; redaction is key-based in the logger format; access logs skip `/health` and log pathname only. Degradation fallbacks always log (no silent `.catch(() => …)`) — fail-open stays observable.
- Identity boundary: Elysia `onBeforeHandle` `as: "global"` in `src/lib/serviceGuard.ts`. Headers `x-service-token` + `x-verified-auth0-id`; missing/wrong/account mismatch → 403. Keep new org/email/auth/me routes under this guard.
- Browser-direct capability routes (`scan.ts`, `analyze.ts`, `chat.ts`, `download.ts`, `status.ts`) never trust a raw `x-auth0-id`. For attribution, the web mints a signed token via `/api/me/attribution/mint` (`src/lib/attribution.ts`, HMAC-SHA256 over `sub.exp`, SERVICE_TOKEN keyed) and sends it as `x-attribution`; the server `verifyAttributionToken()`s it. Add endpoints for minting only under serviceGuard.
- **A UNIQUE constraint with a NULLable column does not constrain anything.** A btree unique index treats NULLs as distinct, so `unique (team_id, member_auth0_id, student_id)` let `(team, member, NULL)` — every coach membership, the common case — be inserted without limit, and any `on conflict (…same cols…)` targeting it never matched, leaving the `do update set role` branch dead code. `team_memberships` now uses `unique nulls not distinct` (PG15+; Neon is on 18). When adding a unique constraint over a nullable column, either use `nulls not distinct` or split it into partial unique indexes — and if you do the latter, remember `on conflict` then needs the same `where` clause. **No fixture can catch this**: they stub `db` as a plain tag function, so it needs the live smoke. The other two nullable unique keys in the schema are deliberate and audited, not to be "fixed": `notifications (auth0_id, dedupe_key)` is partial `where dedupe_key is not null`, since a notification with no dedupe key is not meant to be deduped, and `org_members (org_auth0_id, member_auth0_id)` admits a NULL member on purpose — `inviteOrgMember` keys a pending invite by email alone and `coalesce`s the account in on signup — so the invite insert is a check-then-act with no `on conflict` (a concurrent double-invite of one email is the only way to get a duplicate row; 0 of 852 live rows).
- **A column declared `string` but backed by `timestamptz` is a lie: Bun decodes it to a `Date`.** Any `a.measured_at.localeCompare(b.measured_at)` then throws `localeCompare is not a function` — and only once a collection holds **two or more** rows, because `Array#sort` never calls its comparator for a single element, so a one-row fixture and a one-row smoke look fine. That took out the performance series _and_ every report built from it. Normalize at the boundary where the value enters the domain object (`performance.ts` does it in `getStudentPerformanceSeries`), not defensively at each use. The same class has been re-derived 5 times as a private `toIsoString` (`notificationPrefs`, `consents`, `privacyRequests`, `org/settings`, `userSettings`) — collapse them, don't add a sixth.
- **An explicit `NULL` never falls back to a column `DEFAULT`.** `insert into t (ts) values (NULL)` where `ts timestamptz not null default now()` raises 23502; the default only applies when the column is _omitted_ from the insert list. Use `coalesce($1::timestamptz, now())`. The same trap in a dynamically-built `update … set ${col} = $n${cast}` is a **per-column** cast list: a blanket `?? '::text'` default means any column you forget is cast to text, and Postgres has no text→timestamptz assignment cast, so it 500s with 42804 the moment a client sends that field (`updateScheduleEvent` did, and the web always sends `starts_at`). `updateStudent` and `updateScheduleEvent` now both list every non-text column explicitly.
- **A loose link plus a late org check is a cross-tenant write.** `students.team_id` is not a foreign key, so `where team_id = ?` matches any org's team — a team uuid is globally unique. `deleteTeam` unassigned students _first_ and asked `org_auth0_id` second, so a caller from another org who knew the uuid cleared every victim's player and then received **404**: a refusal that had already mutated another tenant, leaving that org's coach with an empty roster (the scope seam resolves by team_id). Claim the row for the org under `for update` _before_ touching anything it points at, and keep the org predicate in the write itself rather than trusting the caller's earlier check — the route only pins the role floor, so the data layer is the only place this is catchable. Note the return value was never the bug: it returned false under both versions, which is why the smoke asserts the players' `team_id` and not the boolean.
- Row uniqueness for org tables is org-scoped: `attendance UNIQUE (auth0_id, student_id, session_date)` and `performance_metrics UNIQUE (auth0_id, student_id, metric_key, measured_at)`. Keep `ON CONFLICT (…)` targets in `lib/org/*` (e.g. `org/attendance.ts:66`, `org/performance.ts:83`) in sync with these constraint column lists (idempotent migration lives in `ensureInitialized` in `src/lib/historyStore.ts`, the sole DDL owner).
- Supabase helpers live in `src/lib/` (`orgData.ts` — a thin barrel over `lib/org/*`, one module per subdomain — and `historyStore.ts` for schema/DDL). Data-layer functions take optional filter opts (e.g., `getUserAnalyses(…, { unlinked })`) rather than adding query params at the route layer.
- Wrapper-owned init: `withHistoryStore`/`withHistoryStoreOrThrow` share `runWithHistoryStore`, which awaits `ensureInitialized()` before the callback — never `await ensureInitialized()` inside a callback; absorb the disabled/null sentinel with `orDisabledDefault(value, fallback)` (the one no-DB degradation policy).
- Self-scoped handlers derive identity with `requireVerifiedSelf`/`missingVerifiedSelf` (`lib/caller.ts`) — never hand-roll the `x-verified-auth0-id` check; share.ts/auth.ts keep their verified-but-different idiom.
- **A global hook that destructures Elysia's `body` consumes the request stream for every route.** Elysia parses the body when any hook or handler in the chain references it, so a global (`as: 'global'`) `onBeforeHandle` naming `body` forces an app-wide parse and every handler reading the stream itself (`request.json()` / `request.formData()`) throws `Body already used` in the composed app — while standalone route mounts (the shape most unit tests use) keep passing, so the suite stays green and production 500s. Upstream names the mechanism: a Web Standard Request parses once ([life-cycle: Skip Body Parsing](https://elysiajs.com/essential/life-cycle.html)), and hooks apply only to routes after registration ([life-cycle: Order of code](https://elysiajs.com/essential/life-cycle.html)). This took out scan-video upload, both analyze kickoffs, and invite-accept (verified live against the composed server). The guard therefore never references `body`; the one route naming its owner in the body (POST `/api/auth/sync`, `body.sub`) enforces identity in its own handler via `verifyServiceIdentity`. A `request.clone().json()` fallback does NOT save the guard: on routes whose handler declares `body`, Elysia has already consumed the stream before the hook runs, so the clone read fails too (verified: sync 403'd even with matching identity). Caught by the authorization matrix (`tests/authMatrix*`), which drives the real composed app — another reason new routes need a matrix row.
- **App-level `.use(route.use(guard))` barrel wraps are inert.** The `orgRoute.use(orgRoleGuard(...))` wrap in `src/app.ts` fires no member query for barrel routes (verified by trace; same for the aiReports wrap), while file-level guards as in `teams.ts`/`members.ts` do. Handler-level capability/scope checks hold the line regardless, but pin matrix expectations to statuses observed against the composed app, not to the documented floor. Same barrel class, sharper edge: a **global** (`as: 'global'`) hook fires only for routes mounted _after_ its `.use()` — a `.use(limiter)` appended at the end of the chain silently covers nothing (verified: 6 writes at budget 5 all passed; upstream scope table: [plugin: Scope level](https://elysiajs.com/essential/plugin.html)). Register global plugins first; top-level registration does propagate into nested mounts. And a `.use(plugin)`-mounted **onError is instance-scoped even when the plugin is named "global"** — the old `globalErrorHandler` never fired for app routes, so escaping throws surfaced as plain-text 500s with the raw message (leak). Error shaping must be registered inline at the root; the plugin export stays only for the smoke harness. Related: `buildApp()` is not idempotent — it decorates the shared route singletons, so a second call in one process stacks guards. One build per probe process.
- **A token is not an identity: bind invite acceptance to the verified caller.** `acceptInvite` resolves the primary id (`resolveAuth0Id`), loads the `users` row, and requires `email_verified` plus `lower(email) === invite.email` before writing anything — otherwise any holder of the link consumes it, and a mismatched caller gets `{ ok: true }` with no membership. The membership write takes an explicit `memberAuth0Id` (`inviteOrgMemberWithId`); the email-lookup `inviteOrgMember` stays for owner-initiated direct invites only, never the accept path. Rejections answer the uniform `Invalid or expired invitation` and leave the token unconsumed.
- **Static imports evaluate before `mock.module` runs — a probe needing mocks must use dynamic imports.** A probe file with top-level `import routes` binds the real modules first; the mocks then apply to nothing and the probe burns real quota (Redis reconnect loop) or misses stubs. Pattern: `mock.module(...)` calls first, then `const x = await import(...)`. Same reason engine conftest pins `UPSTASH_REDIS_REST_URL/TOKEN` empty: `core/jobs.py` builds a real client at import, and with the quota spent every job call fails (flaking test_service_auth by company).
- **Postgres normalizes `IN` to `= ANY` in constraint definitions.** A `like '%col in%'` discovery query over pg_constraint matches nothing on PG16+; match the column name (`like '%status%'`) instead. This also means the older `org_members_role_check` migration's drop-old step is dead on modern PG (flagged, not fixed here).
- **`LIMIT NULL` is unlimited, so bounded reads default the cap to null.** New `limit` opts on the org list functions bind null when absent (existing callers unchanged) and clamp when present; the export passes explicit caps. CSV cells go through the one `csvCell` in `lib/csv.ts` (findings CSV moved onto it, output pinned by its test).
- **Same-level DDL siblings race on fresh databases.** `ADD COLUMN` + its index in one `Promise.all` level means the index can run before the column exists; same for a `CREATE INDEX` beside its table (clips) and a `CREATE TABLE ... REFERENCES` beside its target (students/teams). Only visible on a fresh `ensureInitialized`, which is why live DBs never caught it — and why CI's ephemeral PG (always fresh) is the only gate that matters here. Fix by merging each pair into one sequential block, and by creating FK targets (`students`, `teams`) in their own awaited level before dependents.
- **One multi-row `ON CONFLICT DO UPDATE` cannot touch the same row twice.** Collapse intra-batch duplicate keys first (last wins = sequential final state). Fan-out pools must precompute exact-once targets synchronously and only parallelize completion — and the test asserting emission order has to sort first.
- **`mock.module` leaks globally across test files in execution order — in-process store tests are order-fragile.** Proven with a minimal repro: file A mocking `./real` without export X breaks file B's `import { X }`, and runtime mocks hijack real modules (a delete test failed 403/500 depending on suite order). Upstream confirms the mechanism: mocking after import still runs the original module's side effects, and neither `mock.restore()` nor `clearAllMocks()` resets `mock.module()` overrides ([Bun docs: mocks](https://bun.sh/docs/test/mocks)). The direction is one-way — leaker first, victim after — and which file lands first is **filesystem readdir order**, which is alphabetical on one machine and scrambled on another. A CI stack trace named the victim and the leaker in one frame: `historyStore.test.ts` asserting on its own stub connection, through `at withHistoryStore (tests/aiReportScope.test.ts:52:61)` — 28 assertions failed reading `Expected: 1 / Received: 0` because `aiReportScope`'s partial `historyStore` mock (whose `orDisabledDefault: (_v, f) => f` returns the fallback unconditionally) had replaced the real module. Fixed suite-wide with **`--isolate`** on the test script, which gives each file a fresh `globalThis` *and* a cleared module registry ([parallel & isolated runs](https://bun.sh/docs/test/parallel): "creates a new `globalThis` … clears the ESM and CommonJS module registries"), the same default Jest and Vitest ship. It is a CLI flag only — `[test] isolate` in `bunfig.toml` is silently ignored, verified. Keep the probe-process pattern too (it is the only thing that gives a file its own `process.env`): ephemeral-DB probes forward `TEST_DATABASE_URL` and mock nothing. Do **not** use `--parallel` to get isolation: every worker shares one `TEST_DATABASE_URL`, so the PG-backed suites would interleave writes in one database.
- **CI must run the package's test script, never bare `bun test`.** The server job ran `bun test` while `server/package.json` said `bun test --timeout 30000`, so the project's own budget never applied and every probe-spawning test inherited Bun's **5s default** (documented default, [test runner](https://bun.sh/docs/test#timeouts)). Each such test spawns a whole `bun` process that transpiles and imports the full server module graph before it can print a result; `orgTeamScope.test.ts` failed at `5005ms` with an *empty* stderr and `exitCode: null` ("killed 1 dangling process"), i.e. the runner killed the probe mid-flight. Same test, same DB, no other suite running: `--timeout 5000` fails, `--timeout 30000` → 42/42 pass in 76s. So: any test whose subject is "does the other process behave" needs a per-test budget in the tens of seconds, and a green local `npm test` says nothing about a CI step that doesn't invoke that script. Root `package.json` now delegates (`bun run test`) instead of re-spelling the flags, so the script is the single place they exist.
- Probe-spawning suites now share `server/tests/spawnProbe.ts` — `runProbeProcess({ probe | script, cwd, env, timeoutMs? })` plus `lastJsonLine<T>(stdout)`. `PROBE_TIMEOUT_MS` is **10s**, measured against every probe in `tests/` on an idle laptop: fastest ~150ms, median ~900ms, worst case ~2.4s (the two that deliberately take real dependencies down and wait for them to time out), so it is ~10x the median and ~4x the worst case. It is deliberately **not** the 30s suite budget, which is the confusion it exists to remove — `Bun.spawnSync` blocks the JS thread, so the runner's watchdog kills the child and reports "timed out after 30000ms" with `exitCode: null` and *no output at all*. Bounding the spawn instead makes a wedged child cost 10s and puts its partial stdout/stderr in the thrown error. Two known outliers declare 20s at their own call site (`degradation.test.ts`, `healthDeep.test.ts`) — keep that exception in the file that can explain it. Two files still call `Bun.spawn` directly, `studentScope.test.ts` and `studentImportTeam.test.ts`, because they are owned by another workstream; if you are diagnosing a hang, check those two first, since the helper's existence does not mean every probe in the suite is bounded.
- **A skip gate on `DATABASE_URL` is a gate on the LIVE Neon database, so it silently switched off every live-SQL test in CI — and the fix for it was reverted, because making those tests run made the rest of the suite 30x slower.** A live-Postgres suite gated on `Boolean(process.env.DATABASE_URL)` is gated on the live URL, and `ci.yml` deliberately leaves `DATABASE_URL` unset — its own comment says "nothing destructive ever runs against Neon from CI" — while exposing the ephemeral Postgres service only as `TEST_DATABASE_URL`/`PERF_DATABASE_URL`. Ten files did this (`analysisAdmission`, `attendancePerformanceScopeSql`, `historyStore`, `notificationIdempotency`, `notificationPrefs`, `notifications`, `orgMembers`, `orgTeamScope`, `scheduleSeasonsScopeSql`, `userSettings`), so **43 tests skip on every CI run** and the live-SQL scope enforcement — `uuidArrayLiteral`'s wire format, the `to`-bound day arithmetic, the two-tier scope SQL, exactly the class the entries above say no fixture can catch — never once executes in CI. The workflow comment claims the exact opposite ("the service keeps them green in CI instead of silently skipped"). **Known open, do not assume it is fixed.** A `tests/liveDb.ts` helper was written and reverted (`3128acd`, `f6b16fd`): it worked perfectly locally — skips 43 → 4, 898 pass, green — and took CI from 138s to past the 25-minute job timeout. The cause is the interaction, not the gate: those ten files are **mixed** suites, hermetic probe tests in the same file as the live block, and once the live block ran, every probe spawn in the file jumped from ~300ms to **exactly 10001ms** — the bounded `PROBE_TIMEOUT_MS` from `tests/spawnProbe.ts` — because the file now holds a live Postgres pool that each `bun` child inherits and waits on. Multiply by the number of probe tests across ten files and the job's whole budget is gone. So a green local run proved nothing here, and the lesson is the general one: **a suite that mixes a live database with process-spawning probes has two coupled costs, and enabling the database half taxes the probe half.** If you retry this, either split those files so the live block lives in a file of its own, or find why the child waits on the pool (the probe sets `DATABASE_URL=''`, so the wait is on an inherited handle rather than a connection) — do not simply raise `PROBE_TIMEOUT_MS`, which is a diagnosis, not a fix. Two sub-traps survive in the abandoned helper and are worth knowing regardless: **empty is not unset** (a `??` chain reads `''` as present, and `DATABASE_URL= bun test` is an ordinary way to spell "not set"; trim and falsy-check each candidate, matching `historyStore`'s own `(process.env.DATABASE_URL ?? '').trim()`), and **flipping the gate alone is not enough** — `historyStore` builds its connection from `DATABASE_URL` at *import* time, so a repaired gate with no re-point leaves the store's `sql` null and every `withHistoryStore` call returns `null` through `orDisabledDefault`, a green run of assertions against nothing. Any such re-point must also clear `ensureInitialized`'s memoised `initPromise` (which `setHistoryStoreConnectionForTests` does), or the second file gets the *first* connection's already-resolved promise and the DDL is skipped entirely.
- **Bun runs `beforeAll` and `afterAll` in registration order, so a helper that wires in one and restores in the other cannot be placed correctly by its caller.** Cost me a wasted cycle while building the reverted `liveDb.ts`, and it will bite the next person who writes that helper. A suite that seeds and cleans up *through* the store needs the store wired before seeding and still connected during cleanup. One `useLiveTestDb()` call registers its `beforeAll`/`afterAll` pair at the same index in both sequences: placed **before** the suite's own hooks it wires the store in first (good) and also restores it to null first, so the suite's teardown dies as an *unnamed hook error* — "History store is not configured" — naming neither the test nor the cause. Placed **after** them, the order inverts and seeding runs unconnected. Exactly one position is right and no call site expresses both halves, so take the work as parameters (`useLiveTestDb({ seed, cleanup })`, running `cleanup` before `restore`) and let the helper own the ordering; ordering by construction beats ordering by discipline. Two neighbours: restore the store *before* closing the connection, or a later teardown holding the wrapper fails with `ERR_POSTGRES_CONNECTION_CLOSED`; and registering hooks inside a `describe.skip` makes Bun count them as **two phantom skipped tests**, inflating the very tally being made honest, so bail out early when there is no database.
- **Importing `me.ts` connects to Redis: `lib/redis.ts` connects on import** (`export const redis = createRedisClient()`), reached via me → queue → jobs. With the shared serverless quota exhausted, a probe importing routes burns quota and hangs in a reconnect loop. Stub `../src/lib/redis` inert (`isLocalRedis: () => true`, `getRedisConnectionUrl: () => null`, `redis: null`) in any probe loading routes that transitively reach it — and never run anything against real Redis (use local `docker compose` or stubs).
- **Scope lookups must join for the org, or one org's teams leak into another's scope.** `listMemberTeamIds` had no org predicate, so `resolveCaller` carried a multi-org coach's foreign teams into `studentScope`. `listMemberTeamIdsInOrg` joins `teams` and filters `t.org_auth0_id`. Renaming it touches every probe that mocks `../src/lib/teams` (11 files) — same hazard as the route-import trap above: run the full suite, not just the new test.
- **Student delete is erasure of private rows, unlinking of club history.** `deleteStudent` claims the row (`for update`, org-scoped) then in one transaction deletes `wellness_checkins` / `training_objectives` / `training_plans` / `team_memberships`-by-student and nulls `analysis_history` + `player_events` student links. `attendance` / `performance_metrics` / `player_consents` cascade, `reports` sets null — verify against `historyStore.ts` DDL before assuming. Ephemeral-Postgres tests (`TEST_DATABASE_URL`-gated, skipped otherwise) must pre-clean FK-less tables by student id: residue from a red run otherwise fails the next green one with a unique violation.
- **`students.team_id` is the scope source of truth; `team_memberships` student rows are the roster mirror — write both.** `addTeamMember(studentId)` wrote only the mirror, leaving the player invisible to the team's coaches. `setStudentTeam` (in `lib/teams.ts`) claims the student, validates the team, updates `team_id`, deletes the org's old mirror rows (join `teams`), and inserts the new one, all in one `db.begin` transaction. POST/DELETE `/teams/:id/members` student branches and PUT `/students/:id` with `team_id` route through it; `player.transferred` fires on any actual team change. `deleteTeam` keeps its bulk unassign + FK cascade (equivalent outcome, one statement). A new import in `routes/org/students.ts` or `routes/teams.ts` breaks every probe mocking `../src/lib/teams` — add `setStudentTeam`/`getTeamMembership` keys (returning null) to all of them, same hazard as above.
- **A period's upper bound is a whole day, but `col <= to::timestamptz` is midnight.** `to` arrives in two shapes and one comparison cannot serve both: the report path passes `period_end`, always a bare `YYYY-MM-DD` (`isDate`-validated in `routes/org/reports.ts` and `routes/aiReports.ts`), and the series route passes a query param that may be a bare date _or_ a full instant. Cast to `timestamptz`, a bare date becomes midnight, so `<=` dropped everything recorded **on the final day** — while the attendance half of the same report (`session_date <= to::date`) kept it, because `::date` has no time component to truncate. Nothing errored; the report was just quietly short, and only on the day the numbers are most likely to matter. `org/performance.ts` now makes the bound **exclusive** and shifts it by a day only when the caller named a day: `col < to::timestamptz + (case when ${toIsDay} then interval '1 day' else interval '0' end)`. `toBound()` computes the flag with the _same_ `isDate` the route validates with, so JS and SQL cannot drift, and the arithmetic stays in Postgres so no timezone leaks into the app. Pin both directions: the negative assertion (an instant earlier in that same day is still excluded) is what stops a blanket "widen to end of day" regression from passing.
- **Locate a bound value by placeholder position, never by its type.** `tests/attendancePerformanceScopeSql.test.ts` found the scope predicate's `scoped` flag with `values.findIndex(v => typeof v === 'boolean')`, on the stated assumption that it was "the only boolean in these queries". Adding the `toIsDay` flag to the same queries made that assumption false, and all five performance cases silently began asserting on the _period_ flag and reading the id list out of the next slot — 5 red tests in an unrelated file, which is the only reason it was noticed. `values` is parallel to the `?` placeholders, so the robust move is to regex the predicate and count the placeholders before the match. This is the general hazard behind "add one more filter param": any type-based locator over a bind list is invalidated by the next filter.
- Analysis admission is one call: `admitAnalysis` (`lib/analysisAdmission.ts`) owns quota → tier → priority → usage; pass `basePriority` 5 (`/api/analyze`) or 10 (`/api/me/analyze`) — don't re-inline the gate or the tier-weight math.
- The broad org route floor is membership, not authorization: every org **write** route must also check a capability via `resolveCaller(auth0Id, request).can('<permission>')` (see `org/attendance.ts`, `org/schedule.ts`, `org/students.ts`). The web mirrors the matrix in `lib/permissions.ts` purely to hide what the server would reject.
- Capability is not scope. Any read or write keyed to a `student_id` also asks `visibleStudentIds(orgAuth0Id, caller.studentScope)` (`lib/org/scope.ts`) — `null` means org-wide, a list means those students only, `[]` means none — and write paths gate on `canSeeStudent(ids, studentId)` before touching the store. Refusals split by operation: a **read** of an out-of-scope target answers 404 so it is indistinguishable from a student that does not exist, while a **write** answers 403 beside the capability gate it follows (a missing capability is always 403). `resolveStudentScope` has two tiers by design: team staff (head/assistant/legacy coach) are narrowed to their assigned teams, while org staff (`analyst`, `medical`) are org-wide because they are never assigned a team and would otherwise see an empty app. `schedule_events` carries a nullable `team_id` where null is a club-wide fixture everyone sees and a set id must be the caller's; a season is hidden only when it holds a match and none of them is the caller's, so an empty season stays visible. A scoped caller may write only its own team's events, never a club-wide one. Rationale and rejected alternatives: `docs/adr/adr-0002-roster-scope-two-tiers.md`.
- The account tree `/api/auth/user/:auth0Id/*` is an **org-scoped path** too, and it is keyed to the _org_: analysis rows are owned by the org, so an unfiltered read there is org-wide, not "the caller's own data" — the web passes `orgCtx.auth0Id`, not the session sub (`app/dashboard/history/page.tsx`). It therefore needs the same scope seam as `/api/org/*`, reached through `accountJobScope(auth0Id, jobId, request, 'read' | 'write')` (`lib/accountScope.ts`) for every job-keyed route (analyses detail, clips, chat, rename, cancel, delete) and, for the findings half, `accountStudentReadable` for the `student_id`-keyed reads plus `canAccessTeam` for a `team_id` trend. Findings ship a CSV export, so that route is the most valuable of the lot to leave unrefused. Scoping `routes/org/*` is not scoping this family — they are separate files with separate histories. `getUserStats` takes the same `studentIds` option for the same reason: its tiles are rendered directly above the History list (`components/dashboard/CoachHome.tsx`), so a coach reading "Total Analyses 20" over a three-row list looked like a bug. A scoped caller's list keeps their own students' rows _and_ their own unfiled uploads (rows with no student belong to whoever uploaded them); the residual is that a scoped caller also sees other people's unfiled uploads, which are attached to no player.
- A share token is **unauthenticated** — the link reader needs no login — so minting or revoking one is a write about the player on the video, not a read of it. `routes/share.ts` keyed the token on `analysis.auth0_id !== verifiedAuth0Id`, and since analysis rows are owned by the _org_ that comparison could only ever pass for the org owner: every coach was refused, and the same bug blocked every revoke. Compare the row (and the token record) against the org in the path, then ask `canSeeStudent`. Share resolves its caller only when `serviceGuardEnabled()`, and the guard captures `SERVICE_TOKEN` at import, so a probe process cannot have the guard both on and off — `shareTokenScope.test.ts` runs it on for exactly this reason.
- **A capability check on the _target_ is not a check on the _job_.** `PUT /api/org/:auth0Id/analyses/:jobId/student` gated `player.manage` and then checked `studentVisible` on the body's `student_id` — which is skipped entirely when the field is absent, i.e. the unlink case. `linkAnalysisToStudent` filters on `server_job_id + auth0_id`, so it is org-scoped but not roster-scoped: a team-A coach could unlink team B's player from their own analysis by sending `{}`. Route every `jobId`-keyed write through `accountJobScope(auth0Id, jobId, request, 'write', caller)`. A write that returns a whole row is also a read: `linkAnalysisToStudent` is `update … returning *`, so the response carried `summary_json` with no `redactWellness`, meaning the §5 medical boundary held on this route's account-tree twin and not here. **A new import in a route is a change to every probe that mocks the module it pulls in** — a partial `mock.module('../src/lib/analyses')` fails the whole probe process with "Export named … not found", which is how 30 unrelated cases went red.
- A role floor is not a scope, and a mount-time guard is not a capability. `orgRoleGuard([...])` applied where a route is mounted in `index.ts` says which roles may reach the handler; only an in-handler `resolveCaller(...).can(...)` says which of them may do this to _whose_ data. Audit for this by reading the handler bodies, not the file: `aiReports.ts` looked covered (guarded at mount) while passing `student_id` straight into the unscoped `buildReportContent`, so a team coach could have an AI report written about another team's player. Any handler that aggregates a student must consult the scope seam.
- Bind a scoped id list with `uuidArrayLiteral(ids)` from `lib/org/scope.ts`, never a raw JS array: Bun sends an array as comma-joined text and the `::uuid[]` cast fails with 22P02. The literal must reach the query as a **bound parameter in the tagged template**, never spliced into `db.unsafe` — `db.unsafe` consumes the `{` of a `'{a,b}'` literal and the query dies with `syntax error at or near "{"`, and it does not bind its own `${}` either. Gate the whole clause with a boolean param when the filter is conditional, so one query shape serves both the scoped and org-wide case. **No fixture test can catch any of this** — they stub `db` as a plain tag function — so a new `any(...)` bind needs the live smoke (`smokeOrgHttp.ts`, gated on `DATABASE_URL`) or a live-Postgres test to be trusted.
- **A table name is not a Bun template parameter.** A tagged template binds `${table}` as `$1`, so the query dies with `syntax error at or near "$1"`. `db.unsafe` is the only way to splice an identifier, and there `${}` is plain string interpolation that **does not bind** — so positional `$1` plus a values array is the shape (`deleteAnalysisChildren`). Note the two traps point opposite ways: a raw JS array reaches `any($1)` as comma-joined text (`malformed array literal`), so an id list must be a Postgres array literal bound as one parameter with an explicit `::text[]` cast.
- **A fail-open wrapper hides a broken assertion as a null.** The retention prune passed a JS array to `db.unsafe`; Bun sent it as comma-joined text and `any($1)` against a `text` column died with `malformed array literal` on the first child table, so `pruneRetention` threw on every run and **nothing was ever pruned** — five tables grew forever while the feature reported as healthy, because `retention.ts` logged the error once a day and `pruned` never rose. Latent only because nothing was old enough yet, and certain to fire on the first eligible row. `retention.test.ts` covers just the `retentionDays()` clamp and no fixture can reach the binding, so it is pinned in the smoke; in a test or probe prefer `withHistoryStoreOrThrow`, which surfaces the failure instead of returning `null` that a `=== 0` assertion reports as a confusing value.
- `orDisabledDefault(value, fallback)` absorbs a `null` into the fallback, so it belongs only where the default exists _because_ the store can be absent. A legitimate `null` from the callback (a row whose `student_id` is NULL is a real answer, not a missing store) silently becomes the fallback — that turned "this analysis has no student" into "no such analysis". Return a discriminating shape like `{ found, studentId }` when `null` and "absent" are both possible answers.
- `/api/email/*` is an **org-scoped path** (`isOrgScopedPath` covers it), so `serviceGuard` admits any member of the org named in the path — membership, not authorization. Every route on that tree needs `emailGuard` (`routes/email.ts`): a capability (`org.invite` / `report.create` / `attendance.write`) plus the team scope on whatever it reads. These routes mail data to a caller-supplied address, so an unguarded one is an exfiltration channel, and hiding its button in the UI protects nothing. `emailRouteGuards.test.ts` captures the mail instead of sending it.
- Notifications: emit only through the named helpers in `lib/notificationEvents.ts` (`notifyAnalysisResult`, `notifyReportReady`, `notifyAttendanceRecorded`, `notifyAiReportFinished`, `notifyMembershipChanged`). Event names live in the dependency-free `lib/notificationEventNames.ts` and are typed against the preference table — an unknown name reads as ENABLED, so a hand-typed `type: '…'` silently ignores a user's mute. A parity test fails if a preference nothing emits, or an emitter with no preference, appears.
- **A seam whose only transport lives in the module it is meant to protect is a cycle, and a cycle is a silent bypass.** `notificationEvents.ts` took `createNotification` as its default `Emit` from `notifications.ts`, and `notifications.ts` also owned the queue handlers that emit — so the two could not call each other, and in practice the handlers hand-rolled `createNotification({ type: NOTIFICATION_EVENT.… })` instead. The seam held **zero call sites** and `notifyMembershipChanged` had none anywhere, so the `membership` preference could never fire. A parity test cannot see that: it reads names, not wiring. The fix is to put the transport in a **leaf** — `lib/notificationCreate.ts` owns `createNotification`, `CreateNotificationInput`, `NotificationRow` and the data normaliser, importing only `historyStore`/`notificationPrefs`/`serverEvents`/`logger`, all of which point away from it — and `notifications.ts` **re-exports** the three names so `dataExport`, the routes and the four test files keep their existing import path. When you extract to break a cycle, check the new module's own imports point away from it before assuming it is a leaf.
- Bind objects to jsonb columns directly (`${obj}::jsonb`), never `${JSON.stringify(obj)}::jsonb` — on Bun's **prepared-statement** path (the default, and what `historyStore` uses) the string form is stored as a JSONB _string_, so every read rejects it as a non-object and silently falls back to defaults. It bit 10 columns: `redactWellness` opens with a `typeof summary !== 'object'` guard, so a string passed through untouched and the medical redaction stopped working on persisted analyses, and `notification.data.href` was `undefined` after a reload so every notification in the bell lost its link — 1,362 notification and 672 audit rows were strings in the live database before `ensureInitialized`'s repair migration unwrapped them (idempotent, and it logs `jsonb_double_encoded_rows_repaired`). **The behaviour inverts on a connection built with `prepare: false`**, where a direct object bind instead throws `invalid input syntax for type json` and the stringify form produces the correct object — so a throwaway probe written that way "proves" the opposite of the truth. `tests/jsonbBind.test.ts` fails if the anti-pattern returns.
- A Redis error that means the plan's request allowance is spent (`max requests limit exceeded` and kin) is fatal for the process: `isFatalRedisError` in `lib/queue.ts` reports it **once** and closes the workers. Never let a worker retry that in a loop — it cannot recover, it keeps the window spent, and it floods the log. Ordinary transient Redis failures (READONLY, ECONNRESET) must stay retryable; treating them as fatal would take the queue down over a blip. Remember serverless Redis quotas are a shared resource: do not burn them on test runs.
- Queue is lazy: importing `lib/queue.ts` connects nothing; `index.ts` calls `startQueueInfrastructure()` first (`stopQueueInfrastructure()` on shutdown), late consumers attach via `onQueueInfrastructureReady(...)`; retry verdicts come from `classifyFailure()`; retention scheduling lives in `lib/retention.ts`.
- Chat stores implement the `Transcript` interface (`lib/transcript.ts`: `playerTranscript` Redis, `dashboardTranscript` Postgres — a seam, not a store merge); parse SSE with `lib/sse.ts` (`parseSseDataEvents`), never hand-split chunks.
- **An engine timeout that is enforced with `with ThreadPoolExecutor(...)` enforces nothing.** `__exit__` calls `shutdown(wait=True)`, so a `raise` from inside the block joins the stuck worker _before_ the error propagates — reproduced at 0.50s raise / 5.00s observed. `_stage_reasoning` now shuts the pool down with `wait=False` on the failure path and `wait=True` only on success. That alone is not enough: the Gemini client also needs a real timeout, because the SDK passes `timeout=None` to httpx, which reads as _wait forever_, so a hung request held its thread permanently and two of them wedged the 2-worker analysis executor. Both halves are pinned by `engine/tests/test_gemini_timeout.py`, which drives the real stage.
- **A test that abandons a `ThreadPoolExecutor` worker hangs pytest at _exit_, not at run time.** `shutdown(wait=False)` releases the _caller_ — which is the thing such a test asserts — but the parked worker stays blocked, and `concurrent.futures.thread._python_exit` (an atexit hook) `join()`s every worker at interpreter shutdown. So pytest prints its summary and the process then never exits. The symptom points the wrong way: the engine suite's 289 tests passed in 4.4s and the `engine (Python)` job still died 15 min later with an orphan `pytest` for the runner to reap, which reads as a slow suite and invites raising `timeout-minutes` instead of finding it. `test_a_future_that_never_completes_is_released_by_the_timeout` parked its one worker on a never-resolved `Future`, which no timeout can ever wake; the fix is to resolve it and `shutdown(wait=True)` in a `finally`. Confirmed on 3.12 **and** 3.14 (`_python_exit` is byte-identical in both), so it is not a pinned-version trap and a newer local venv reproduces it just as well — what makes it hard to spot is that nothing is slow, the process simply never returns. Only _bounded_ work is ever safe to abandon, which is exactly what the client's own finite timeout gives `_stage_reasoning` above. Verify by running the suite on the pinned 3.12 (`engine/Dockerfile` `python:3.12.14-slim-trixie`, `ci.yml` `python-version: "3.12"`) under `timeout` and checking the process _exits_, not that the summary printed.
- **A model-supplied number is untyped input.** `int("8.5")` raised inside the render loop and leaked both cv2 handles plus a half-written mp4, after the Gemini call had been paid for; `validator` checks summary fields for presence but never type, and `quality_check` coerces with `float()` so `"8.5"` passes as in-range. Coerce defensively at the consumer (`renderer._coerce_score`) _and_ release in a `finally`.
- A metric named `*_extension` / `*_alignment` is scored as 180° = straight. The elbow metric was the complement — it differenced two bone _directions_, so a straight arm read 0.0° and basketball's highest-weighted criterion (weight 0.20, ideal [160,175]) told a player with a perfect release to fix it; differencing `arctan2` results is also wrong across the ±pi branch cut (~335° for a nearly-straight arm). Use dot/cross, which has no branch cut, and match the convention `compute_joint_angles` already uses. Pinned by `engine/tests/test_tracking_elbow.py`, including a branch-cut sweep and a monotonicity assertion.
- The local-storage sweep must be **recursive**: writers namespace keys under `raw/<session>/<angle>/` and `results/`, so a one-level `glob("*")` plus `isfile` matched the two directories and deleted nothing — one rendered mp4 per analysis accumulated forever. Resolve the root the same way the writers do (`ENGINE_ROOT`-relative, not CWD-relative) or a launch from a different directory skips it. Pinned by `engine/tests/test_storage_sweep.py`, which also asserts the old shape finds zero files.
- Engine owns code → HTTP status + `retryable` (`engine/core/errors.py` `STATUS_BY_CODE`/`RETRYABLE_BY_CODE`); routes derive status only via `enginePassthroughStatus`/`chatEngineStatus` and send bodies through `errorBody(...)` — never re-map codes to statuses; `JOB_NOT_FOUND` is `retryable: false` on every path.
- **A malformed id is a 400, and the boundary is the only place that knows it.** An unvalidated `student_id`/`session_date`/`:id` reaches a `::uuid`/`::date` cast, raises 22P02 or 22007, and is reported as **500 INTERNAL_ERROR** — by any member, including a read-only one. The sharpest instance was inside one file: `attendance`'s batch route validated its date and the single-record route 50 lines above it did not. Use `pickUuid` (optional) and `UUID_RE.test` (required path param) from `lib/uuid.ts` — the SSOT, and `pickUuid` replaces three local copies that had drifted. Also `pickInt` for `limit`/`offset`: `Number('abc') || fallback` already absorbed NaN and `Math.max` floored a negative offset, so that one was **not** a live bug (I checked before claiming otherwise) — `pickInt` is a clarity and single-contract win, and its one real trap is that `Number('')` is `0`, so `?limit=` would clamp to `min` and silently truncate a list. 21 smoke assertions pin the 400s; they fail under mutation with the exact `status: 500`.
- A `catch` that returns a fallback still needs a log line: fail-open stays observable. The three that were silent — `engine.markEngineJobFailed`'s connectivity branch (the engine's job state stays `running` forever), the rate limiter's Redis→memory fallback (with the quota spent, _every_ request silently switches stores), and `serviceGuard`'s two identity catches (a Neon blip denies every non-owner org request with zero signal, while the sibling `caller.ts` logs the identical class as `member_role_lookup_failed`) — now log `engine_job_failed_not_delivered`, `rate_limit_degraded_to_memory`, and `member_role_lookup_failed` / `org_role_lookup_failed`. All four keep their fail-closed/fail-open **behaviour**; only the silence is gone. **No test asserts these four lines actually fire** — asserting them needs a `mock.module('../src/lib/logger')` harness that does not exist yet, so they are the one part of this round that is read-verified but not runtime-pinned. Note the rate-limiter case is the one that bites hardest in practice: a spent serverless quota routes every single request down that path, and nothing distinguished it from normal operation.
- **A bulk endpoint's size cap is a work-limiter, not a validation nicety, and the cap must fire before the loop.** `setAttendanceBatch` upserts one entry at a time _sequentially_ inside the single request, so `POST /attendance/batch` cost was linear in `entries.length` while the route checked only `Array.isArray(entries) && length > 0` — any member holding `attendance.write` could post 50,000 entries and hold the request open. `MAX_ATTENDANCE_BATCH = 500` mirrors `MAX_IMPORT_ROWS` (a class of 30 over a fortnight is ~40 entries). The testable part is not the 400, it is that **`calls.setAttendanceBatch` stays 0** — a cap checked after the writes have already happened is not a cap. Pin both sides of the boundary (`MAX + 1` refused, exactly `MAX` accepted) or a one-off in the comparison passes both. A batch cap of `N` also means `to` validation and the scope check are reachable only for ≤ N rows, so keep the size check **before** them.
- Rate limiting + ids:429s come from `rateLimited()` (`src/lib/ratelimit.ts`); validate ids against `UUID_RE` (`src/lib/uuid.ts`). Don't hand-roll either.
- Engine HTTP surface: routes live under `engine/api/` (mounted by the thin `engine/main.py`); session-token mint/validation and upload cleanup live in `engine/sessions.py`.
- Engine tests must never inherit a developer's `engine/.env`: `engine/tests/conftest.py` pins `SERVICE_TOKEN` and `SENTRY_DSN` to empty before `main.py` imports (the service-token middleware 403s every non-`/health` route once `SERVICE_TOKEN` is set, and a real DSN ships test events to Sentry). `tests/test_service_auth.py` owns the identity boundary with its own `monkeypatch`. CI runs without a `.env`, so a leak here is invisible until someone's machine runs it.
- Sport vocab SSOT is `engine/core/sport_config.py` (positions/aliases/pack versions) — served through the guard-exempt `GET /sports/{sport}/positions`.
- Email: `src/lib/mailer.ts`. `RESEND_API_KEY` unset → routes return 501 `EMAIL_NOT_CONFIGURED` by design; smoke asserts it.
- Env: documented in `server/.env.example` and `web-next/.env.example`; keep them in sync with `process.env` reads.
